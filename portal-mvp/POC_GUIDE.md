# Management Console PoC — 0.5

기존 VC 검증기를 유지하면서, 한 계정이 **VC 등록 → 참여 세션 연결 → 서비스 제공 또는 계약 → 고정 주소 데이터 조회 → 초기화 → 재연결**을 실행할 수 있습니다.

## 0.5 변경: 역할 모델

Gaia-X에서 Participant는 단일 주체이고, Provider/Consumer는 계정 속성이 아니라 **서비스 오퍼링·계약 단위에서 맡는 역할**임. 0.4는 "관리자 = 운영자 겸 유일한 제공자, 일반 가입자 = 소비자" 구조였으므로 이를 분리함.

| 구분 | 0.4 | 0.5 |
|---|---|---|
| 웹 가입 계정 | 소비자 (서비스 등록 불가) | **참여자** — VC 검증·세션 연결 후 제공과 이용 모두 가능 |
| 서비스 등록 | 관리자 전용 | 참여 세션이 연결된 참여자 누구나. 운영자는 대상 참여자 콘솔에서 대신 등록 가능 |
| 서비스 소유 | 없음 (포털 자체) | `owner_account_id`, `provider_participant_id`, 등록에 쓴 VC 세트 기록 |
| 계약 기록 | 이용자만 | 이용자 + `provider_participant_id` |
| 관리자 | 운영자 + 제공자 | **운영자(operator)** — 계정·전체 로그·서비스 삭제·플랫폼 샘플 등록. 참여 역할과 분리 |
| 운영자 판정 | `PORTAL_ADMIN_USERS` 환경변수 | DB `accounts.is_operator` (환경변수는 하위 호환으로 계속 인정) |

규칙:

- 자신이 제공하는 서비스는 계약 불가. 같은 회사 VC를 쓴 다른 계정(동일 participant ID)도 불가.
- 제공자가 등록에 사용한 VC 세트를 삭제하거나, 재검증 실패·유효기간 만료 시 해당 서비스는 **제공 중지**. 카탈로그에서 계약할 수 없고 기존 계약의 데이터 요청도 거부됨.
- 제공자의 세션 만료·초기화만으로는 제공이 중지되지 않음 (24시간 세션과 서비스 수명 분리).
- 다른 참여자가 등록한 원본 API 주소(`data_url`)는 제공자 본인과 운영자에게만 노출.
- 외부 API origin은 **데이터 API origin 허용 목록**(allowlist)에 있어야 등록·호출 가능 (참여자 등록에 따른 SSRF 방지). 운영자 콘솔에서 즉시 추가·해제하며 재배포 불필요.
- **플랫폼 샘플**: 운영자가 VC 없이 등록하는 연결 테스트용 서비스. `demo://weather`만 허용. 실제 API는 참여자로 등록해야 함.
- 0.4에서 등록된 서비스는 소유자가 없으므로 플랫폼 서비스로 표시되며 계속 동작함. 실제 제공자에게 귀속하려면 해당 참여자 계정에서 재등록 후 기존 서비스 삭제.

## 실행

Python 3.11 이상. 기존 실행 방법과 SQLite DB 경로를 유지합니다.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
python -m pip install -r requirements.txt
python portal.py --port 8000
```

브라우저에서 `http://localhost:8000`을 엽니다. 웹에서 가입한 계정은 모두 참여자이며, 처음 가입한 사용자가 자동으로 운영자가 되지는 않습니다.

### 운영자 생성 (서버에서만)

운영자는 참여 역할이 아닌 플랫폼 관리 권한이므로 웹 가입으로 부여하지 않습니다. 서버를 종료한 상태에서 아래 명령을 실행합니다. 기존 계정 이름을 지정하면 비밀번호가 재설정되고 운영자 권한이 부여되며 해당 계정의 로그인 세션이 해제됩니다.

```bash
python manage_admin.py --username admin --port 8000
```

비밀번호는 표시되지 않는 입력창으로 받습니다. 권한은 DB에 기록되므로 **환경변수 지정 없이** 그대로 서버를 실행하면 됩니다.

```bash
python portal.py --port 8000
```

권한 해제 (계정·VC·서비스는 유지, 로그인 세션 해제):

```bash
python manage_admin.py --username admin --port 8000 --revoke
```

서버 실행 포트와 명령의 포트가 같아야 동일 DB를 사용합니다. 콘솔에서 권한 승격은 제공하지 않습니다. 0.4 방식의 `PORTAL_ADMIN_USERS` 환경변수도 계속 운영자로 인정하므로, 해제할 때는 환경변수에서도 제거하세요. 이름 `admin`과 환경변수에 지정된 이름은 웹 가입이 막혀 있습니다.

## 시연 순서

참여자 두 곳(제공 역할 A, 이용 역할 B)에 서로 다른 회사의 non-production VC가 필요합니다.

1. 참여자 A 가입/로그인 → **VC 관리** → VC/VP 업로드 → 검증 항목 확인 → **세션 연결**.
2. A → **서비스 제공** → `demo://weather`(또는 허용된 실제 API base URL)와 국가 `KR`로 서비스 등록.
3. 로그아웃 → 참여자 B 가입/로그인 → VC 업로드 → 세션 연결.
4. B → **카탈로그 · 이용** → 제공자가 A로 표시된 서비스 계약.
5. **ping 테스트**, **데이터 테스트** 실행. 응답 확인.
6. A로 다시 로그인 → **서비스 제공** → "내 서비스 이용 계약"에 B가 표시되는지 확인.
7. **활동 및 검증 로그** → 해당 작업 펼침 → 세부 검사 결과 확인.
8. B → **연결 현황** → 세션 종료·초기화. 같은 주소의 ping/데이터 조회가 거부되는지 확인.
9. A → VC 삭제 → B의 카탈로그에서 해당 서비스가 **제공 중지**로 바뀌는지 확인.

VC가 한 세트뿐이면 운영자가 **운영자 콘솔**에서 플랫폼 샘플 서비스를 등록해 이용 흐름만 시연할 수 있습니다.

**테스트용 통과 VC를 프로그램에 내장하지 않았습니다.** 제공된 VC가 기존 검증기를 통과해야 실제 콘솔에서도 연결됩니다. API 통합 테스트는 성공 보고서를 테스트 안에서만 대체하며, 실행 서버에 검증 우회 기능은 없습니다.

## 콘솔 기능

| 영역 | 핵심 기능 |
|---|---|
| 연결 현황 | VC 세트 수, 참여 세션 만료, 활성 계약 수, 세션 초기화, 키 재발급 |
| VC 관리 | 파일 업로드, 세트별 재검증·연결·삭제, 문서별 상세 검사 결과 |
| 서비스 제공 | 서비스 오퍼링 등록·삭제, 제공 상태(제공 중/중지 사유), 내 서비스를 계약한 참여자 목록 |
| 카탈로그 · 이용 | 제공자 표시, 서비스 계약·해지, 고정 URL 표시/복사, ping·griddata 테스트 |
| 활동 및 검증 로그 | 시각, 작업, 실행자, 대상 계정, 결과, HTTP 상태, 처리 시간, 검사 단계, 50건 단위 조회, 결과 필터 |
| 운영자 콘솔 | 전체 계정·권한 조회, 대상 참여자 콘솔 관리, 데이터 API origin 허용 목록 관리, 플랫폼 샘플 등록, 전체 서비스 조회·삭제, 전체 로그 조회 |

운영자는 대상 참여자의 콘솔에서 VC 업로드·재검증·삭제, 세션 연결·초기화, 서비스 등록(해당 참여자 명의), 계약·해지, 키 재발급을 수행할 수 있습니다. 운영자도 VC 검증·국가 정책·자기 서비스 계약 금지를 우회하지 않습니다. PoC에서는 서비스 정책 수정 대신 삭제·재등록합니다.

## 상태 간 관계

- **접속 키:** 계정당 1개. 재연결/초기화/VC 삭제에도 주소는 유지됩니다. 키 재발급 시에만 변경됩니다.
- **참여 세션:** 계정당 1개. 최대 24시간이며 VC·검증 결과 유효기간을 넘지 않습니다.
- **서비스 계약:** 계정 + 해당 세션 + 서비스에 연결. 만료는 세션·VC 기간 이내입니다.
- 세션 재연결 시 기존 계약을 해제합니다. 새 세션에서는 서비스를 다시 계약합니다.
- VC 세트 삭제 시 그 세트를 사용하는 세션과 계약을 해제합니다. 다른 세트는 유지됩니다.
- 초기화 시 세션과 계약만 해제합니다. VC·고정 키·활동 로그는 남습니다.
- 서비스 삭제(제공자 본인 또는 운영자) 시 그 서비스의 모든 계약이 해제됩니다.
- 제공자 VC 세트 삭제·검증 실패·만료 시 서비스는 삭제되지 않고 제공 중지 상태가 됩니다.
- 같은 회사 VC를 서로 다른 계정에 등록해도 계정별 계약과 데이터 접근은 분리됩니다.
- 접속 키는 만료되지 않습니다. **24시간 후 만료되는 것은 세션입니다.** 노출된 키는 재발급해야 합니다.

## 데이터 API origin 허용 목록

외부 데이터 API는 허용 목록에 있는 origin(`scheme://host[:port]`)만 쓸 수 있음. 목록은 두 출처의 합집합임.

| 출처 | 관리 방법 | 콘솔에서 해제 |
|---|---|---|
| 서버 설정 | `PORTAL_ALLOWED_DATA_ORIGINS` 환경변수 (쉼표 구분) | 불가, 서버 재시작 필요 |
| 콘솔 | **운영자 콘솔 → 데이터 API origin 허용 목록** | 가능, 즉시 반영 |

- 등록 시 정규화: scheme·호스트 소문자화, 기본 포트(80/443) 제거. `HTTPS://API.Example.com:443`과 `https://api.example.com`은 같은 origin으로 처리.
- 경로·쿼리·계정정보가 붙은 입력, http/https 외 scheme은 거부.
- 콘솔 등록은 `localhost`, `*.internal`, `*.local`, 사설·루프백·링크로컬(169.254.169.254 메타데이터 포함) 등 공인 인터넷이 아닌 IP 리터럴을 거부. 내부망 API가 꼭 필요하면 서버 설정으로만 허용.
- 해제하면 그 origin을 쓰는 서비스는 삭제되지 않고 즉시 **제공 중지**. 등록·호출·계약이 모두 거부됨. 다시 허용하면 복구.
- 목록 화면에 origin별 사용 서비스 수, 등록 운영자·시각, 메모가 표시되며 추가·해제는 활동 로그에 남음.
- 참여자는 서비스 제공 화면에서 현재 허용된 origin 목록을 확인할 수 있음.
- 한계: 공인 도메인이 내부 IP로 해석되는 경우(DNS rebinding 등)는 막지 못함. 호출 시 DNS 결과를 고정·검사하는 기능은 없음.

## 실제 Weather API 연결

외부 API 요청은 포털이 대행합니다. 별도 컨테이너는 필요 없습니다.

```bash
# 운영자 콘솔에서 https://weather-api.bmap.kr 을 허용 목록에 추가해도 되고,
# 고정 기준선으로 두려면 환경변수로 지정
PORTAL_ALLOWED_DATA_ORIGINS=https://weather-api.bmap.kr python portal.py --port 8000
```

운영자가 origin을 허용하면, 제공 참여자가 서비스에 `https://weather-api.bmap.kr/api`와 같이 **API base URL**을 등록합니다. 이용 참여자에게 표시되는 주소는 다음 형태입니다.

```text
https://gaia-x-portal.bmap.kr/access/{고정키}/{service_id}
```

| 이용 참여자 요청 | 처리 |
|---|---|
| GET {base}/ping | 키·세션·VC·계약·국가 정책·제공자 상태 점검 |
| GET {base}/griddata?source=... | Weather API base + /griddata에 쿼리 전달 |
| GET {base}/latest?... | Weather API base + /latest에 쿼리 전달 |

서비스 UUID를 경로에 사용합니다. 별도 slug 관리 기능은 추가하지 않았습니다. 허용 경로는 `ping`, `griddata`, `latest`입니다. 다른 Weather API 경로가 필요하면 allowlist를 명시적으로 확장해야 합니다.

외부 API는 리디렉션을 따르지 않고 인증 헤더를 전달하지 않습니다. 응답 최대 5MB, 타임아웃 30초입니다. 데이터는 크기 제한 내에서 메모리에 버퍼링한 뒤 반환합니다. 실제 API 주소·쿼리·응답 스펙과 Web-ECDIS의 연동은 별도로 확인해야 합니다. **샘플 JSON은 실제 격자 데이터 형식을 재현하지 않습니다.**

`/ping`, 연결, 계약은 전체 재검증합니다. 데이터 요청은 기존 검증기의 재검증 조건(60초/credentialStatus 등)을 그대로 유지합니다. 이번 변경에서는 캐시 정책을 완화하지 않았습니다.

## 서버 노출 설정

기본 허용 호스트에 `gaia-x-portal.bmap.kr`, `35.212.206.187`, localhost가 있습니다. 다른 호스트·브라우저 origin은 다음 환경변수로 지정합니다.

- `PORTAL_ALLOWED_HOSTS`: 쉼표 구분 호스트명 (스킴 제외)
- `PORTAL_ALLOWED_ORIGINS`: 쉼표 구분 브라우저 origin (스킴·포트 포함)
- `PORTAL_ALLOWED_DATA_ORIGINS`: 외부 데이터 API origin의 고정 기준선 (운영자 콘솔 등록분과 합산)

외부 제공 시 HTTPS reverse proxy를 사용하세요. 앱은 TLS 인증서 설치나 DNS 설정을 수행하지 않습니다. URL의 키를 로그에 남기지 않도록 `python portal.py` 실행의 Uvicorn access log를 끕니다. 다른 방식으로 실행하면 `--no-access-log`를 지정하세요. Nginx 등 앞단에서도 `/access/` 경로의 access log를 끄거나 키를 마스킹해야 합니다.

PoC의 고정 주소 재표시를 위해 SQLite에 키 원문을 함께 저장합니다. DB 파일 접근을 제한하고 공유하지 마세요. 로그에는 비밀번호·원본 JWT·접속 키·쿼리·요청 본문을 기록하지 않습니다. 로그는 SQLite에 보관되며 변조 방지 감사 저장소는 아닙니다.

## 호환성 및 검증 범위

- 기존 SQLite 테이블에 필요한 컬럼/테이블을 자동 추가합니다. 업데이트 전 `data/`를 백업하세요.
- 기존 계정과 VC는 유지합니다. 계정/세션 귀속 정보가 없는 구버전 계약은 사용할 수 없으므로 재연결·재계약하세요.
- 루트 페이지는 새 `console.html`입니다. 기존 `dashboard.html`은 참고 파일로 보존하되 제공하지 않습니다.
- `/service-offerings` 등록은 참여 세션이 연결된 참여자(또는 `platform_sample: true`인 운영자)만 가능합니다. `X-Portal-Local`만으로는 관리할 수 없습니다.
